**Status:** architecture recommendation for independent review; no production changes are authorized by this document.

## 1. Executive architecture decision

### Recommendation

Use a **static React + TypeScript + Vite single-page application**, served by the existing **Caddy** ingress and connected to the existing **FastAPI** application on same-origin browser routes. FastAPI remains the only application authority for authentication, authorization, URL policy, analysis, and resource budgets. Keep the Chrome extension on its current bearer-token contract and keep Streamlit private until the new UI has verified workflow parity.

For the first access-controlled demonstration, use a narrowly scoped FastAPI-owned login for individually allowlisted users, with Argon2id password verifiers provisioned out of band, opaque server-side sessions, and CSRF protection. Make the browser-auth router explicitly disabled by default; when enabled in a deployment, fail closed if its account source or allowed app origin is missing. Keep the first browser analysis vertical slice deterministic and AI-off. Do not put `API_ACCESS_TOKEN`, `DASHBOARD_API_ACCESS_TOKEN`, or any shared work credential in Vite variables, JavaScript, browser storage, or a proxy header forwarded to anonymous users.

The smallest initial deployment remains **one API process behind Caddy**. A bounded, process-local session store and the existing process-local rate-limit model are acceptable only for that single-instance private demonstration: process restart invalidates all sessions, capacity exhaustion denies new logins, and multi-process or multi-instance operation is unsupported. Public multi-user exposure requires a separately approved identity and shared-budget architecture. No database, queue, Redis, microservice, or SSR runtime is proposed for the first slice.

### Why this shape

- It reuses the existing analyzer, SafeFetcher, typed response models, extension contract, Caddy ingress, and container boundary instead of replacing them.
- A same-origin SPA avoids browser CORS for its own API calls, but **same origin and CORS are not authentication**. Each browser work endpoint must validate the session and CSRF token in FastAPI.
- A separate browser API namespace avoids silently changing the extension's bearer-authenticated routes.
- Vite has no production server requirement for this application. No SSR requirement has been established; Next.js would add a second server and identity/proxy boundary without removing the need for FastAPI authorization.
- Server-side session storage is needed to revoke a browser session on logout. A bounded in-process store is the least infrastructure for a single-process private demo; it is deliberately not a public or horizontally scaled design.

## 3. Approved product and design constraints

### Product boundary

The primary user is a site owner, editor, or small content team making a page-level improvement. The central workflow is:

> Enter URL → receive bounded HTTP/static-HTML observations → review deterministic rule statuses → inspect evidence and explanation → make a change outside SEO Sensei → submit again and compare manually.

The first slice is one user-submitted URL per request; it is not a site crawler, ranking tracker, monitoring service, publication system, or saved-report workspace. There is no existing persistence or report identity.

### Evidence labels that must survive implementation

| Data shown | Truthful provenance label | Must not imply |
|---|---|---|
| Status, headers, elapsed time, byte count, final URL | HTTP response/transport observed by SafeFetcher | Browser rendering, user-perceived speed, indexing, or Googlebot’s view. |
| Title, description, robots directives, headings, links, images, structured data, social metadata | Parsed from fetched static HTML and supported response headers | Arbitrary source-node locations, page JavaScript DOM, intent, quality, or third-party validation. |
| `pass`, `warning`, `fail`, `not_applicable`, category points, `0–100` score | Deterministic v1 analyzer heuristic | Business severity, commercial priority, Google ranking, actual index state, traffic, or a Google score. |
| Gemini output, if later enabled | Optional AI-generated suggestion with explicit unavailable/error state | Observed fact, independently verified advice, or score input. |
| Search Console, PageSpeed/Core Web Vitals, actual index state, traffic, rankings, backlinks, authority, competitors | **Unavailable today** | Do not display them as measured. A future integration needs an authorized source and separately approved contracts. |

`SEOCheck` contains `id`, `category`, `title`, `status`, point values, `evidence.observed`, optional `evidence.value`, and `recommendation`; it contains no business-severity field, arbitrary DOM snippet, or source location. The 92/100 in the approved fixture is a heuristic score and must remain visually secondary to an observed `noindex` directive. A fixture excerpt is not a production API capability.

### Capability priorities

- **Core:** deterministic URL analysis; fetch context; the 23 existing checks; findings search/status/category navigation; evidence → interpretation → suggested action → verification; honest empty, loading, blocked, timeout, unavailable, and retry behavior; repeat request without saved history.
- **Secondary after the vertical slice:** report export from returned fields; before/after comparison while clearly distinguishing two user-submitted responses and deciding whether any data is retained.
- **Optional after cost and privacy approval:** Gemini recommendations, opt-in per request, isolated from score/status, budgeted and clearly labelled.
- **Retain temporarily:** article generation and SEO boost remain available to existing clients/dashboard until consumers are inventoried. Article generation is a separate AI writing feature. SEO boost repeats analysis before proposing a description; decide later whether to consolidate, keep separate, or remove after product/consumer review.
- **Exclude absent a new source/decision:** rank tracking, traffic, backlinks/domain authority, competitor metrics, actual indexing, Core Web Vitals, keyword volume, rich-result eligibility, and whole-site crawling.

### Approved Evidence Ledger presentation

Preserve the accepted Phase 1C system in `docs/design-phase-1c-handoff.md`: warm-neutral surfaces, Georgia/Iowan/Palatino serif display stack, Segoe UI/Arial interface stack, Consolas evidence stack, text-first findings, thin structural rules, restrained statuses, secondary score, no sticky/fixed bars, and compact mobile report context. Preserve its exact token/breakpoint/component table rather than inventing a new design system. The handoff's 200% browser zoom, keyboard activation, fixture error recovery in-browser, and screen-reader checks are **not verified**; see section 11.

## 4. Target system diagram and trust boundaries

### Proposed topology

```mermaid
flowchart LR
  U[Site owner or editor browser<br/>untrusted client] -->|HTTPS: page requests| C[Caddy public ingress<br/>TLS, static files, routing]
  C -->|GET / and hashed assets| W[React + TypeScript + Vite build<br/>static, no server credential]
  U -->|same-origin cookie + CSRF header<br/>POST /api/browser/v1/*| C
  C -->|preserve /api/browser/v1 prefix| B[FastAPI browser router<br/>session auth, CSRF, per-user limits]
  B -->|existing analyzer orchestration| F[SafeFetcher + deterministic SEO engine]
  F -->|bounded HTTP(S), validated public destinations| X[Untrusted external website]
  B -. later, explicit opt-in only .-> G[Gemini provider<br/>external processor and quota]
  E[Chrome extension<br/>separate user-configured bearer] -->|API_DOMAIN, existing /analyse-url etc.| C
  C -->|legacy route only| L[FastAPI legacy bearer routes]
  L --> F
  S[Streamlit dashboard<br/>legacy, private during transition] -. private/admin route only .-> C
  C -->|private Compose network; no published API port| B
  C -->|private Compose network| L
```

### Trust boundaries

1. **Browser → Caddy:** browser input, URL, search text, cookie, and all displayed source/AI strings are untrusted. TLS terminates at Caddy. Browser code contains no server secret. App uses a host-only session cookie and same-origin API path.
2. **Caddy → static application:** only static Vite build assets are served. Use a history fallback for SPA routes; never let an API path fall through to `index.html`. Hashed assets may be long-cacheable; `index.html` is revalidated. API and login/session responses are `Cache-Control: no-store`.
3. **Caddy → FastAPI:** containers remain on a private network; only Caddy publishes host ports. Caddy forwards `/api/browser/v1/*` without stripping the prefix on the app hostname. FastAPI, not Caddy alone, validates the session, CSRF token, origin, request schema, rate budget, and authorization. Only the configured Caddy network is trusted for forwarded IP/scheme/host. Never trust a client-supplied identity header.
4. **API domain / extension:** the existing API hostname remains the extension boundary with explicit CORS origins and its current bearer routes. Caddy should deny `/api/browser/v1/*` on the public API hostname as defense in depth. Even if routing is misconfigured or the API is addressed directly, browser routes require a valid app session and CSRF proof; bearer auth is not accepted as a fallback there. Existing extension routes still enforce bearer auth inside FastAPI.
5. **FastAPI → SafeFetcher:** target URLs are untrusted. Existing URL policy, DNS pinning, redirect revalidation, timeouts, response limits, and fetch-wide lock remain the controlled egress boundary. No browser or frontend component fetches the submitted website.
6. **FastAPI → Gemini:** optional external processor. First browser analysis forces AI off. Later AI requires an explicit user choice, content disclosure, budget checks, and safe rendering of output.
7. **Streamlit transition:** current public routing must be restricted immediately. Keep Streamlit on a private/admin-only route or private Compose network until workflow parity is accepted; never leave the current unauthenticated dashboard route public during migration.

### Caddy path contract

The app host serves `/` and static files from the Vite build. It matches `/api/browser/v1/*` first and reverse-proxies that exact prefix to FastAPI. FastAPI mounts the browser router under the same prefix. Use Caddy `handle` (or an explicit tested rewrite) if preserving the prefix; `handle_path` strips its matched prefix. Caddy documents the distinction explicitly: [`handle`](https://caddyserver.com/docs/caddyfile/directives/handle) is mutually exclusive routing; [`handle_path`](https://caddyserver.com/docs/caddyfile/directives/handle_path) strips the prefix. Apply a body cap to this new app-host API route as well as the existing API-host route; today the Caddy request-body cap is configured only in the API host block. Validate route order and direct API-host denial with Caddy validation and request tests. Keep the existing `API_DOMAIN` legacy route and 1 MB Caddy cap.

## 5. Authentication options and recommended model

### Options

| Decision criterion | **A. External access-controlled demonstration** | **B. FastAPI-managed restricted-user sessions — recommended** | **C. Public multi-user identity — future only** |
|---|---|---|---|

| Credential/session management | Provider stores user credentials and manages its browser session. **Assessment:** Option A may reduce password/session code, but its identity provider and signed assertion contract have not been selected or verified. Option B is the recommendation for a one-process private demonstration because the backend can enforce and test the whole browser-work boundary without relying on an unspecified platform. Option C is explicitly outside this phase and is not approved. An external gate can still be added as defense in depth, but is never the sole work authorization unless its verifiable identity contract is separately approved.

### Recommended restricted-user model (proposal, not approved implementation)

- **Identity/provisioning:** no public registration, self-service reset, or shared demo password. An operator provisions individual named users out of band. Store only Argon2id password verifiers in a read-only deployment secret file; never store plaintext passwords or place passwords in CLI arguments/logs. Use a maintained implementation, benchmark it on the small container, and meet at least OWASP's current Argon2id baseline (19 MiB memory, 2 iterations, parallelism 1) unless measured resource constraints justify a reviewed change. [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) recommends adaptive password hashing rather than reversible encryption/plaintext. Missing or malformed production account configuration fails closed.
- **Feature/config gate:** `BROWSER_AUTH_ENABLED` is false by default so pre-existing API deployments can continue serving their current bearer clients before the new web deployment is ready. When enabled, missing/malformed user verifiers, app origin, session bounds, or production cookie configuration fails closed for browser auth. Do not let the browser work routes fall back to bearer credentials.
- **Login and authorization:** `POST /api/browser/v1/session/login` over HTTPS accepts a bounded username/password JSON request; generic failure text avoids account enumeration. Use a dummy verifier path for unknown usernames where practical. Login throttles by trusted client IP, a non-reversible account key, and a bounded process-wide cap. The response sets a new session cookie; all work operations must use the session dependency. Do not use login state from the browser as authorization.
- **Session representation/storage:** 32 random bytes from a CSPRNG, URL-safe encoded; cookie contains only the opaque random value. Store a hash of the session identifier, user ID, CSRF verifier, issue time, last activity, and absolute expiry in a bounded in-memory store. Do not encode identity/permissions in the cookie. Refuse new sessions at the configured capacity; do not evict active sessions to make room. This store is supported only for the current one-process deployment; restart invalidates all sessions. Do not add Uvicorn workers or API replicas until shared session/rate-limit storage is approved.
- **Expiry/revocation/fixation:** proposed initial policy is 30-minute idle and 8-hour absolute expiry, enforced server-side (both are design values to approve and tune). Generate a fresh ID only after successful authentication; reject client-supplied IDs; delete the server record on logout and clear the cookie. Credential changes or account removal take effect on controlled restart and revoke all sessions. If immediate per-user revocation without restart is required, replace the in-memory store with a reviewed shared store/IdP before expanding the demo. OWASP recommends server-side idle/absolute expiry, logout invalidation, and regeneration at authentication; it gives 15–30 minutes and 4–8 hours as typical low-risk examples. [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
- **Cookie:** `__Host-seo_sensei_session`, `Secure`, `HttpOnly`, `SameSite=Lax` (explicit; use `Strict` if the navigation trade-off is accepted), `Path=/`, no `Domain`, and an expiry no later than the server absolute timeout. Do not store session or API tokens in `localStorage`, sessionStorage, or Vite env. Production `Secure` is mandatory. Development uses `localhost` only or local HTTPS; never provide a production config that silently downgrades the cookie.
- **CSRF and origins:** use a synchronizer token tied to each server session, returned by an authenticated same-origin bootstrap endpoint and held only in app memory; send it in `X-CSRF-Token` for every state-changing browser request, including logout and analysis. Require exact configured `Origin` equality for login and state-changing requests; reject absent or `null` Origin rather than guessing from an untrusted Host. Accept no broad `*.example.com` origin. Use `SameSite` only as defense in depth. Keep GET/HEAD side-effect free. The SPA uses same-origin requests, so it does not need credentialed CORS. OWASP recommends synchronizer tokens for stateful apps and strong Origin checking; absent/null origin is not evidence of same-origin. [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- **Rate/cost budgets:** login is throttled separately. Browser work budgets key by authenticated user/session and trusted client IP and include a process-global crawler cap. Initially run one FastAPI process and keep AI disabled in the browser route. Numeric thresholds need an operator budget decision; do not silently inherit bearer-token defaults as user budgets. Before public/multi-instance use, replace process-local user/global budgets with a shared store or a verified upstream control and prove restart/replica behavior.
- **Secrets and environment:** account hashes belong in a protected, read-only deployment secret file; API bearer and Gemini secrets remain server-side. Rotate the legacy API token independently. Environment variables or Docker mounts must not enter the Vite build. Protect secret files, restrict container access, and never print their values in health, exception, CI, or diagnostic output.
- **Direct backend bypass:** production Compose keeps API ports unpublished; Caddy remains the only network ingress. Session checks live in FastAPI, not only a Caddy path rule. Caddy denies browser namespace on API_DOMAIN; if that rule is bypassed, the browser router still rejects bearer-only/anonymous requests. CORS remains an origin policy, never the auth decision.
- **Local development:** use a loopback-only Vite server and FastAPI, with Vite proxying `/api/browser/v1` to FastAPI; keep production cookie policy and app origin explicit. Use HTTPS locally if the browser cannot exercise `Secure` cookies on localhost. Test values/accounts are non-production, never committed. Fail closed if `APP_ENV=production` lacks a configured account source or allowed app origin.

### External gate coexistence

An external access gate may be added in front of the private app as defense in depth after a host/provider is selected. It cannot replace FastAPI checks. If it supplies a user assertion, the assertion must be cryptographically verified by FastAPI (issuer, audience, signature/algorithm allowlist, expiry, and identity); Caddy must not trust or forward arbitrary unsigned identity headers. Test the `API_DOMAIN` bypass path separately. If the provider cannot meet this contract, keep FastAPI sessions or stop and request an explicit architecture decision; do not substitute a shared proxy token.

### Error and request behavior

1. Client validates a URL string for usability; server Pydantic validation remains authoritative. Invalid/malformed input returns a bounded `422 invalid_url`/`invalid_request` response.
2. Unsupported schemes return a stable `422 unsupported_url` response. SafeFetcher rejects private, loopback, link-local, reserved, malformed numeric and unsafe redirect targets before network access. Map policy rejection to a distinct stable client error (recommended `403 destination_blocked`) rather than `502 resource_unavailable`; do not disclose resolved private addresses.
3. DNS failure, timeout, HTTP error, wrong content type, and fetch-size rejection remain sanitized remote-resource failures (typically `502 resource_unavailable`) with request IDs. Exact codes/status mapping needs a contract test and compatibility review because API-01 currently misclassifies blocked destinations.
4. The UI presents explicit pending, timeout, unsupported/blocked, upstream failure, rate-limited, session-expired, AI-unavailable, and no-result states. A browser abort/timeout must not claim server work was cancelled unless cancellation is confirmed.
5. A failed reanalysis keeps the prior in-memory result visible with a clear failure banner; it does not create a saved history item or claim a comparison. A successful repeat replaces the current in-memory result. No report timestamp/ID exists in the API.
6. First browser request must use `include_ai_recommendations=false` or a narrower URL-only browser request schema. If optional AI is absent, deterministic findings remain complete. A fixture is allowed in tests and an explicitly labelled local demo mode only; a failed production API response must never silently fall back to fixture data.

### Extension boundary

Keep `frontend/` as the extension. Continue its configured API origin, optional host permission prompt, locally stored user-supplied bearer token, and existing root routes. Its token remains visible to that browser profile's user as the extension documentation already warns; do not ship one to a public/untrusted audience. The browser SPA receives a session cookie, not this bearer token. Keep explicit extension-origin CORS on the API hostname, but no credentialed cookie CORS. Add contract checks for legacy request/response/error shapes before any route refactor.

## 9. Data/API integration plan

### First browser workflow

1. Browser obtains an authenticated FastAPI session through same-origin login. The session cookie is `HttpOnly`; the browser gets a CSRF token separately and keeps it only in memory.
2. URL form performs local usability checks, then `POST /api/browser/v1/analyse-url` with the URL and same-origin cookie/CSRF header. It never fetches the URL itself.
3. FastAPI validates session, CSRF, exact origin, request size/schema, per-user/IP/global limit, then calls the existing orchestration path and the existing `SafeFetcher`/deterministic engine.
4. First slice forces AI off. It returns the existing deterministic analysis shape; the UI validates the response and renders source/transport facts, heuristic check statuses, and explanations. No HTML source excerpt or location is synthesized.
5. User can navigate overview → findings → detail while the result stays in memory. Reanalysis issues a new explicit request. A failed second request keeps the prior response and states that the new request failed; it does not claim a saved snapshot or comparison.

### Contract boundaries and failure states

- **Input validation:** `URLAnalysisRequest` currently uses `HttpUrl`, max length 2,048, `include_ai_recommendations=false` by default, and `extra="forbid"`. Keep server validation authoritative. Decide whether the browser namespace uses the same schema or a narrower URL-only schema; do not silently expose article/boost or AI controls in the first slice.
- **Fetch-policy rejection:** invalid input (422), unsupported scheme (422), blocked destination/unsafe redirect (recommended distinct 403), and remote fetch failure (sanitized 502) must be visibly distinct enough to guide correction without revealing internal DNS/address details. Add exact code/status contract tests; legacy extension compatibility must be checked.
- **Timeout/retry:** set browser timeout deliberately relative to server SafeFetcher deadline. Show timeout and a user-triggered retry; do not replay POST automatically. Keep request ID available for support without including submitted URL in logs.
- **Response validation:** parse the error envelope and required analysis shape; malformed responses show a safe API error and request ID. Never render raw JSON as the primary UI or HTML-interpret page/AI strings.
- **AI missing/failure:** deterministic checks and score remain usable. First browser route does not request AI. A later explicit opt-in may receive existing typed `AIRecommendationsResult` states; unavailable/timeout/invalid response is supplementary, never a reason to discard deterministic analysis.
- **Fixtures:** use fixtures in unit/component/E2E tests and an explicit local development demo only. Label demo data, never run it as a fallback when FastAPI is down. Production failure must remain a failure state.
- **Do not add contract fields in this plan:** no severity/business priority, Google index status, rank, traffic, source excerpt/location, report ID/history, CWV, or competitor/backlink fields. Any such request requires product justification, schema/version proposal, and approved source/retention semantics.

## 12. Local development and deployment plan

### Local development

- Run Vite on loopback and FastAPI on loopback. Configure Vite's development proxy for `/api/browser/v1/*`; the browser sees same-origin paths and the server secret never enters Vite. Do not configure CORS as a substitute for auth.
- Keep production cookie `Secure` behavior. Use localhost browser secure-context support only after testing the actual target browsers; otherwise use local TLS. Do not add a config mode that allows non-secure cookies on a non-loopback or production host.
- Use an explicit development account/test hash and test-only secrets. Never use production credentials in `.env`, fixtures, browser environment variables, or CI.
- For API tests, inject a deterministic fake SafeFetcher/transport through test-only dependency/lifespan seams. Do not relax the production URL policy to make localhost crawls possible. Do not call public websites or Gemini in CI.
- Keep fixture-only app mode explicitly labelled. A fixture can test UI, not prove API integration.

### Production/static topology

- Build `web/` with `npm ci` and immutable lockfile. Recommended deployment uses a multi-stage Caddy image: Node builds `dist/`; existing pinned Caddy runtime serves those static assets and continues TLS/ingress. This avoids a Node service at runtime. Review build context and `.dockerignore` so `.env`, account hashes, API/Gemini secrets, and local artifacts cannot enter image layers.
- Caddy app host serves static files with SPA fallback and routes `/api/browser/v1/*` unchanged to FastAPI. Route API before file fallback and apply the request-body cap to this route. Caddy API host preserves the legacy extension API routes, keeps its existing body cap, and rejects the browser namespace. Caddy route order and prefix behavior are covered by config validation plus HTTP integration tests.
- Compose publishes only Caddy `80/443`; API and Streamlit remain on private networks. Keep only Caddy as trusted forwarded-header peer. Do not expose the API container for browser convenience.
- Readiness checks confirm local API initialization, not Gemini or external-site reachability. Static UI may load while API is unavailable; render a clear service error and no fake data. Decide whether API health is separate from static-site health.
- Hashed JS/CSS use long immutable cache; `index.html` is short/no-cache; every authenticated API/error/session response is `no-store`. No cached user analysis or URL.
- Caddy access logs should not retain request bodies, Authorization, Cookie, submitted target URLs, or sensitive query strings. Current code removes headers and the `token` query key; review whether query filtering should be stricter for the SPA. App logs should keep request ID, route, method, status, and duration only. Define retention/access before public exposure.
- Keep security headers/CSP compatible with Vite assets and same-origin API; no third-party fonts/scripts. Validate CSP in browser and avoid inline script exceptions.

### CI, deployment protection, and rollback

- Extend CI with package lock verification, frontend type/lint/test/build, fixture/schema contract checks, Playwright browser flows, axe smoke, existing Python suite, `security_checks.py`, Caddy/Compose validation, both image builds, and container/dependency scanning. Keep Gemini and external sites mocked/offline.
- Treat low-cost hosting as a goal, not a price or availability guarantee. Select a host only after verifying its TLS, secret, private-network, persistent-volume, Caddy, and access-control capabilities from current official docs. Public/multi-user rollout additionally needs per-user identity, shared quotas, abuse handling, provider budget, operational alerting, and privacy/retention approval.
- During transition, route legacy Streamlit only through a private/admin-gated surface; preserve its container/API client for rollback. Keep the previous Caddy config and image tag available. No deployment changes occur in this planning stage.

## 13. Integration and rollback strategy

### Git integration

The accepted audit and design commits descend from the original main baseline but are not currently on `main`. After Phase 1D is approved, create a deliberate, reviewable integration PR from the accepted design history into `main` before or alongside implementation. Confirm `main` is still based on the audited source, identify the exact commits/files in the PR, and preserve the audit and approved Phase 1C handoff in history. Do not cherry-pick only the prototype UI while losing its evidence/contract context, and do not silently rebase or rewrite accepted history.

The integration PR may retain Phase 1A/1B explorations as design archive initially. Defer archive/pruning decisions until the shipped app and approved Evidence Ledger are verified. If the repository wants a smaller long-term tree, move redundant experiments only in a separate reviewed cleanup after the audit/evidence value is decided. Start the first production feature branch from the resulting integrated `main` so it does not reintroduce the old baseline or omit accepted artifacts.

### Functional rollback

- Auth foundation is additive; legacy bearer routes remain available. If browser session tests fail, disable the browser router and keep Streamlit privately gated.
- UI/API integration can be disabled by reverting Caddy's SPA/API route and restoring the previous known-good Caddy/API image pair; do not point public ingress back to unauthenticated Streamlit.
- With the recommended no-persistence, one-process session model, deployment restart intentionally logs out all browser users. There is no report-data migration or history rollback.
- Any future score v2 or API error contract change has versioned tests and explicit extension compatibility before rollout. Keep the previous score version/code or a rollback release until result compatibility is accepted.
- Streamlit, extension, compatibility wrappers, tests, docs, and security utilities are not cleanup targets until consumers and parity are evidenced.

## 14. Open decisions and assumptions

1. **Approve the auth model:** named allowlisted FastAPI sessions (recommended) versus a chosen identity-aware gate with a cryptographically verified backend identity assertion. If the user count grows beyond the private demo, revisit identity provider and shared session/rate-limit storage before exposure.
2. **Approve session policy:** account provisioning format/owner, 30-minute idle and 8-hour absolute defaults, max in-memory sessions, logout/account revocation expectation, one Uvicorn process, and exact public app origin. These are proposals, not existing settings.
3. **Choose deployment host/domain and private gate:** current repository config can run Caddy/Docker, but no public deployment was inspected. Costs, persistent secret injection, private-user restrictions, and external gate capabilities are unknown.
4. **Approve additive API namespace and error mapping:** `/api/browser/v1/*`, session-only dependencies, URL-only deterministic analysis, and blocked-destination error code/status. Confirm legacy extension behavior before altering root routes.
5. **Set crawler and future AI budgets:** per-user/session/IP/global limits, owner of Gemini spend, opt-in disclosure, provider output retention, and whether browser AI remains off until an explicit later release.
6. **Decide article generation and SEO boost:** separate optional tools versus consolidate/remove; inspect external consumers and current user value first. Extension's unwired boost helper and compatibility wrappers are not enough evidence for deletion.
7. **Approve scoring v2 scope:** thresholds, N/A math, canonical/robots semantics, heading parse, alt purposes, JSON-LD validation level, score label and compatibility policy require domain review.
8. **Complete deferred design verification:** real 200% zoom, keyboard activation/focus/history, direct fixture failure/recovery, automated accessibility, reduced motion, and screen reader remain unverified at the accepted Phase 1C commit.
9. **Decide report retention/export/integrations:** there is no database/history today; any saved report, Search Console, PageSpeed, source-node location, or external measured data needs explicit privacy, provenance, contract, and cost approval.
10. **Dependency/deployment policy:** choose frontend lockfile/package manager, scanner/SCA threshold, container base-image update cadence, browser matrix, and support/monitoring budget before production exposure.

## 15. Proposed exact scope of the first production implementation prompt

**This is a proposed prompt for later approval only. Do not execute it as part of Phase 1D.** It is intentionally the authentication foundation, not the frontend or analysis integration.

> On a new feature branch from the approved, integrated `main`, implement only the FastAPI browser-session foundation for the allowlisted private-demo model specified in `docs/engineering-phase-1d-plan.md`.
>
> **Files in scope:** add `backend/app/api/browser_auth.py` and `backend/app/security/browser_sessions.py`; update `backend/app/config.py` and `backend/app/main.py` only to validate/register the new configuration/router; add a pinned Argon2id implementation to `requirements-api.txt`; add focused `tests/test_browser_auth.py` and `tools/provision_browser_user.py` for offline account provisioning. Update only the relevant security/development docs if needed for safe local use. Do not modify the existing root analysis/article/boost routes or extension source.
>
> **Required behavior:** `BROWSER_AUTH_ENABLED` defaults false so the current API can continue serving existing bearer clients before deployment is ready. When enabled, production fails closed if the allowlist/account-hash source or allowed app origin is missing. Individually named, pre-provisioned users only; no public sign-up/password reset; Argon2id password verification without plaintext persistence; generic failed login; bounded per-IP/account/global login throttling; a fresh cryptographically random opaque session ID stored server-side only in a bounded single-process store and hashed in that store; no client-supplied session IDs; Secure/HttpOnly/host-only `__Host-` cookie; approved idle/absolute expiry; server-side logout/expiry revocation; synchronizer CSRF token; exact Origin enforcement and rejection of absent/null/wrong origins for state-changing routes; no state-changing GET; no CORS-based authorization; no auth/session secret in logs; no fallback from browser session auth to bearer auth or vice versa. Restart clears all sessions and is documented. Existing bearer routes and their tests remain unchanged.
>
> **Tests:** valid/invalid login; generic unknown-user response; login rate limits; cookie attributes; session rotation/fixation attempt; malformed/expired/revoked session; logout invalidation; CSRF missing/wrong; Origin missing/null/wrong; capacity fail-closed; missing production config; no password/session value in logs; regression tests proving legacy bearer routes still accept only the configured bearer and browser auth grants them no access.
>
> **Stop conditions:** do not create `web/` or React/Vite files; do not add the protected analysis route; do not change Caddy, Compose, Dockerfiles, extension, scoring, Gemini, Streamlit exposure, or existing API contracts; do not deploy or call external sites/providers; do not introduce a database, Redis, or multi-worker behavior. If secure account provisioning, cookie behavior, session bounds, or testable revocation cannot be completed within this scope, stop and report the concrete blocker rather than weakening the boundary.

The user/supervisor must approve the authentication model and this first-task scope after independently reviewing the plan. Until then, the only authorized change in this Phase 1D branch is this planning document.
